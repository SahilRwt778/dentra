# Prescription and visit-summary PDFs

The API generates PDFs from saved clinical records. Patients can open them from a completed appointment or **My Records → Visits → Visit summary**. The dentist can preview/download a signed prescription during consultation and both documents after completion.

## Availability and access

- `GET /appointments/:appointmentId/prescription/pdf`: active patient owner after visit completion, or the active verified treating dentist after signing. An unsigned, empty or cancelled prescription cannot be exported.
- `GET /appointments/:appointmentId/visit-summary/pdf`: active patient owner or active verified treating dentist, after completion.
- Other patients/dentists receive 404. Admins receive 403. All content requires bearer authentication, uses `private, no-store` caching and has no public file URL.
- Mobile downloads use the existing private cache and phone PDF viewer. Logout/session loss clears the cache; downloads finishing after an account switch are discarded. Saving or sharing from the viewer is controlled by the user.
- Dentist web opens a PDF preview with a download action. Temporary browser object URLs are revoked when closed or unmounted.

Prescription PDFs include patient details, age at the visit, dentist qualification/registration, clinic details when applicable, the saved medicine list, instructions and the signing date. The confirmation text describes the application's signing-code verification; the PDF does not contain a cryptographic certificate, handwriting image, OTP or internal signing reference.

Visit summaries include the saved complaint, findings, diagnosis, treatment, plan, follow-up, recorded dental-chart changes and a signed prescription when present. No medicine or advice is generated by the export code.

Treatment plans also contain an optional ordered `planItems` array: each item records a procedure, permanent FDI teeth (an empty list means general treatment), and an optional integer `estimatedCostPaise`. Up to 20 procedures can be saved independently through the existing consultation PUT endpoint. Omitting the array preserves it; sending `[]` clears it. Estimates are displayed with the procedures in mobile, dentist web and immutable visit-summary PDFs. Existing snapshots without the array remain valid. Apply migration `1792828800000_consultation_treatment_plan.sql` on databases created before this feature.

`followUpDate` is a calendar date (`YYYY-MM-DD`) or `null`. Omit it from a consultation PUT to preserve the saved date; send `null` to clear it. Invalid dates and timestamps are rejected. The API returns the same date regardless of the server timezone. Dentist mobile provides a calendar picker in Plan and can save changed sections before completing a consultation; completion creates the same immutable document snapshot as dentist web.

## Snapshots

Migration `1792252800000_care_documents.sql` creates the private `care_documents` table. A prescription snapshot is inserted in the signing transaction; a summary snapshot is inserted in the completion transaction. If either operation fails, its snapshot rolls back too. Later profile edits do not change the saved document.

Existing signed/completed records are captured on their first PDF export, under the appointment lock. These PDFs explicitly state that historical profile details were captured at first export. Snapshot rows are retained with the clinical record. No endpoint modifies or deletes them; a future record-amendment feature will need explicit document versioning.

## Setup

Use Node 22.23.2. In `dentra-api`, install dependencies, run `npm run migrate -- up`, then build/restart the API through your usual workflow. The Nest build copies the bundled fonts into `dist`; deployments must include those assets.

No new native mobile package is needed for this feature. Reload the existing patient app after updating its JavaScript. The previously installed private-file viewer is reused. Real SMS delivery remains deferred; the existing signing OTP development stub still logs the generated code in the API console.

## Layout and fonts

PDFKit renders static text/vector A4 documents with repeating headers, numbered footers and automatic pagination. The API embeds Noto Sans and Noto fonts for Devanagari, Gurmukhi, Tamil and Bengali. Source fonts and their license are bundled in `dentra-api/src/modules/care/documents/fonts`; they are not fetched at runtime. See the [official Noto archive](https://github.com/notofonts/noto-fonts) and [PDFKit text documentation](https://pdfkit.org/docs/text.html).

Unsupported glyphs return a clear export error rather than silently dropping or changing clinical text. The saved record remains intact and readable in the app. There is a 100-page export limit; text is never silently truncated.

Synthetic sample PDFs can be regenerated without accessing the database or starting a server:

```sh
cd dentra-api
npm run build
node scripts/sample-care-documents.cjs
```

The samples are written to `output/pdf/` at the workspace root. For PDF text inspection and optional PNG rendering, use `node scripts/inspect-care-pdf.mjs path/to/document.pdf path/to/png-directory`. These local inspection tools are development dependencies, separate from runtime generation.

## Manual test

1. Book an appointment, start the consultation as its dentist and save notes/medicines.
2. Confirm that an unsigned prescription offers no PDF export. Sign it using its generated signing code.
3. Preview/download the prescription on the dentist web. Confirm that it contains the saved medicines, instructions and registration details.
4. Complete the consultation. Open both PDFs as the dentist.
5. In the patient app, open the completed appointment or its visit summary in My Records. Download the summary and signed prescription and check the native viewer's save/share action.
6. For a completed visit without medicines, confirm that only the summary download is offered.
7. Change a profile name and download the document again; its recorded identity must remain unchanged. Another user must not be able to retrieve that appointment's PDF.

Automated tests verify PDF text, ownership, active-account checks, signing/completion gates, concurrent historical exports, snapshot rollback, pagination, supported fonts, unsupported-character errors, token refresh, private caching, viewer actions and account-switch isolation. Integration tests use a disposable schema and synthetic data.
